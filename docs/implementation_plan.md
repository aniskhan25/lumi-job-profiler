# Post-Job GPU Feedback & Education Loop
## Detailed Implementation Plan (Software Development Focus)

This document specifies implementation-level details for building the post-job feedback and education loop on LUMI (AMD GPUs, ROCm stack). It is written for a mixed HPC systems + software engineering team and focuses on data flow, components, interfaces, and logic (not timelines or costs).

---

## 1. System Architecture Overview

### 1.1 Current User-Facing Architecture

```text
User sbatch script
  | source profile_hook.sh
  | profile_run / profile_start / profile_stop
  v
Node-local metrics sidecar
  |
  v
Per-node raw logs
  |
  v
Local summarizer
  |
  v
summary.json
  |
  v
Analysis and reports
```

### 1.2 Stable Workflow Contract

Current user-facing interface
- User clones the repo to shared scratch
- User sources `bin/profile_hook.sh` in an existing `sbatch` script
- User either wraps the main command with `profile_run -- <command>` or uses manual lifecycle control with `profile_start`, `profile_stop`, and `profile_summarize`

Current execution model
- A lightweight `rocm-smi` sidecar is launched with `srun`
- Raw per-node logs are written under `/scratch/project_462000131/$USER/lumi-profile/$SLURM_JOB_ID/`
- A local summarizer converts raw logs into `summary.json`
- Higher-level analysis and reporting consume `summary.json`

Design principle
- Preserve the current opt-in workflow as the stable collection interface
- Add richer metrics, analysis, and reporting behind that interface
- Avoid forcing users to rewrite working `sbatch` scripts as the system evolves

### 1.3 Target End State

```text
User sbatch script
  | source profile_hook.sh
  | profile_run / profile_start / profile_stop
  v
Node-local collectors ---> Local summary artifacts
                              |
                              v
                        Metrics ingest / storage
                              |
                              v
                        Analysis + heuristics
                              |
                              v
                        Reports + recommendations
                              |
                              v
                        User delivery (files / email / portal)
```

Transition model
- Phases 0 to 3 can run entirely from user-space artifacts generated by the current hook
- If cluster-wide hooks are adopted later, they should reuse the same summary schema and analysis pipeline

## 2. Data Collection Layer

### 2.1 Job Identification & Metadata

Source
- SLURM environment variables
- `sacct`, `scontrol`
- Job launch context (`srun` or `sbatch`)

Captured fields
- `job_id`
- `user_id`
- `project_id`
- `job_name`
- `partition`
- `nodes`
- `gpus_requested`
- `gpus_per_node`
- `walltime_requested`
- `walltime_used`
- `exit_code`

Implementation
- Captured in user space during summarization or post-processing
- Serialized as JSON
- Stored in local summary artifacts first, then in central job records if a backend is added

### 2.2 GPU Metrics Collection

Collection mechanisms
- ROCm SMI (`rocm-smi`) sampling
- Slurm GPU accounting (where available)
- Lightweight sidecar process per node

Metrics
- GPU utilization (sampled, per GPU)
- GPU memory usage (avg / peak)
- GPU active vs idle time
- GPU count with non-zero utilization

Optional ROCm-specific metrics (if available)
- `gfx_clock` (core clock), `mem_clock`
- `power` (average / peak)
- `temperature`
- `pcie_bandwidth`

Sampling strategy
- 1 to 5 second sampling interval
- Rolling aggregation on node
- Summary statistics only forwarded

ROCm sampling caveats
- `rocm-smi` counters can vary by GPU model and driver version
- Prefer per-GCD or per-GPU consistency checks before aggregating
- Document missing fields explicitly instead of zero-filling

Current output artifacts
- Per-node raw logs written during job execution
- One `summary.json` file per job

Near-term implementation priorities
- Version the raw log and summary schema
- Harden parsing against LUMI-specific `rocm-smi` formats
- Add test fixtures from real LUMI logs

Output format
```json
{
  "job_id": 123456,
  "node": "nid00123",
  "gpu_id": 0,
  "avg_util": 22.1,
  "p95_util": 41.3,
  "peak_mem_gb": 14.2
}
```

### 2.3 CPU & Process Metrics

Metrics
- CPU utilization per task
- CPU wait / idle time
- MPI rank count
- Threads per rank

Purpose
- Infer CPU bottlenecks
- Detect GPU oversubscription or undersubscription

Rollout note
- CPU and process metrics should be added as an optional extension to the current sidecar
- The existing GPU-only workflow should remain the default lightweight mode

## 3. Metrics Ingest & Storage

### 3.1 Ingest API / Daemon

Responsibilities
- Accept metric payloads from compute nodes or post-job summarizers
- Validate schema
- Associate metrics with job records
- Perform basic aggregation

Design
- Phase 0 and 1: no central ingest required; local summary artifacts are sufficient
- Phase 2+: stateless service for uploads from job summaries
- Writes to time-series or relational store
- Backpressure-safe (drop raw samples if overloaded)

### 3.2 Data Storage Model

Tables / collections
- `jobs`
- `gpu_metrics_summary`
- `cpu_metrics_summary`
- `job_efficiency_results`

Key design decision
- Store aggregated summaries only, not full traces
- Retain raw samples only for short diagnostic window (optional)
- Treat `summary.json` as the stable interchange artifact between collection and analysis

## 4. Analysis Engine

### 4.1 Efficiency Metric Computation

For each job:

Derived metrics
- Average GPU utilization (job-wide)
- Peak GPU memory usage
- Effective GPUs used

```text
effective_gpus = sum(util_gpu_i > threshold) / total_gpus
```

- GPU-hours wasted estimate

Near-term analysis milestones
- Enrich `summary.json` with job-level derived metrics
- Add time-above-threshold and active-GPU counts
- Add job metadata needed for downstream reports

### 4.2 Job Classification Logic

Efficiency classes
- Efficient: >= 70%
- Acceptable: 40 to 69%
- Inefficient: 15 to 39%
- Wasted: < 15%

Stored as
```json
{
  "job_id": 123456,
  "efficiency_class": "INEFFICIENT",
  "avg_gpu_util": 21.3
}
```

### 4.3 Root-Cause Heuristic Engine

Rule-based inference
- Low GPU util + low memory -> overscaling
- Low GPU util + high CPU -> CPU bottleneck
- Util drop after start -> I/O or sync
- High GPU count + few active GPUs -> parallelism mismatch

Implementation
- Deterministic rule set
- Multiple causes allowed
- Each cause tagged with confidence score
- Start with GPU-only rules, then add CPU and job-structure-aware rules

## 5. Recommendation Engine

### 5.1 Resource Right-Sizing

Logic
- Suggest GPU count based on:
- Effective GPUs used
- Peak memory footprint
- Scaling efficiency estimate

Example
```json
{
  "recommended_gpus": 2,
  "reason": "Only 2 GPUs showed sustained utilization >30%"
}
```

### 5.2 Job Script Modification Generator

Inputs
- Original `sbatch` options
- Recommendation results

Outputs
- Diff-style suggestions:

```text
--gpus=8        -> --gpus=2
--ntasks=16     -> --ntasks=2
```

No automatic modification; advisory only.

Workflow impact
- Recommendations should be emitted as additional artifacts
- Existing profiled jobs should not need to change how they invoke the profiler

## 11. Observability & Maintenance

### 11.1 System Health Metrics

- Missing job reports
- Collector failures
- Analysis latency

### 11.2 Safe Failure Modes

- If metrics missing: generate partial report
- Never block job completion
- Never auto-cancel jobs

### 11.3 Compatibility And Regression Risk

- Preserve `profile_hook.sh` as the stable user interface
- Treat new metrics as additive; avoid breaking existing `summary.json` consumers
- Keep lightweight profiling as the default mode
- Introduce deeper profiling only through explicit opt-in flags

## 13. Phased Implementation Roadmap

### 13.1 Phase 0: Current Stable Demo

Deliverables
- `profile_hook.sh`
- `rocm-smi` sidecar sampling
- `summary.json` generation
- Lightweight opt-in workflow for existing `sbatch` scripts

User workflow impact
- No change required; this is the baseline to preserve

### 13.2 Phase 1: Harden Collection And Summary

Deliverables
- Versioned raw log format
- Versioned summary schema
- Parser tests using real LUMI logs
- Richer job-level derived metrics in `summary.json`

User workflow impact
- No change to `profile_run` or manual lifecycle usage
- Existing scripts continue to work

### 13.3 Phase 2: Add Rule-Based Analysis

Deliverables
- Efficiency classification
- Root-cause heuristics
- Recommendation artifacts

User workflow impact
- Same profiling commands
- Additional output files next to `summary.json`

### 13.4 Phase 3: Add Report Generation

Deliverables
- Markdown and HTML reports
- Lightweight visual summaries
- Issue-to-documentation mapping

User workflow impact
- Same collection workflow
- Better post-job outputs

### 13.5 Phase 4: Add CPU And Job-Structure Context

Deliverables
- Optional CPU metrics
- MPI and Slurm job-structure metadata
- Better bottleneck attribution

User workflow impact
- Default mode should remain unchanged
- Optional environment flags may enable richer collection

### 13.6 Phase 5: Add Central Storage And Delivery

Deliverables
- Metrics ingest service
- Persistent job history
- Email or portal delivery

User workflow impact
- Local artifacts remain available
- Central services augment the workflow rather than replace it

### 13.7 Phase 6: Optional Deep Profiling

Deliverables
- `LUMI_PROFILE_MODE=deep-trace` as an explicit opt-in mode
- `rocprofv3`-based trace collection under `deep_profile/trace/`
- `deep_manifest.json` and trace summaries that sit alongside the existing lightweight artifacts
- Debug-oriented deep analysis of GPU trace artifacts without changing the default lightweight path

User workflow impact
- Enabled only through explicit opt-in
- Lightweight default remains the recommended path
- Existing `profile_run` and summary/report artifacts remain available in deep mode

Current scope decision
- Implement only `deep-trace` backed by `rocprofv3`
- Do not depend on ROCm Systems Profiler / `rocprof-sys` in the active roadmap
- Treat ROCm Systems Profiler as future work pending a supported install path on LUMI

## End State

The implemented system produces consistent, actionable post-job feedback, reinforces efficient GPU usage behavior, and creates a data foundation for fair scheduling and policy decisions without introducing punitive or intrusive controls.
